# 실제 서버 접근 확인

개인 접속값과 매뉴얼 추출본은 루트 `.gitignore`로 제외한 `dev/.private/`에서만
관리한다. 인증값, OTP, 내부 IP와 호스트 키는 이 문서에 복사하지 않는다.

## 매뉴얼 확인 및 2026-10-31 재시험

- 제공 매뉴얼 5쪽의 주석에 실제 공공존 VPN 도메인이 있다. 화면 예시 도메인과
  구분하여 개인 접속 파일의 `vpn.url`에 기록했다.
- 5–7쪽은 Agent 등록과 연결 시 이메일/SMS OTP 절차를 안내한다. 사설 IP로
  SSH를 시도하기 전에 VPN 연결과 대상 경로를 확인해야 한다.
- 현재 Mac은 macOS 27.0.1이다. 공식 다운로드 페이지의 지원 목록은
  macOS 12/13/14/15/26이고, 확인 당시 Agent는 1.1.4다. **27의 호환성은
  확인되지 않았다.** 처음에는 설치를 보류했고, 이후 사용자가 현재 Mac의 시험
  설치를 명시적으로 승인했다.
- 샌드박스 밖에서 두 서버의 SSH를 각 1회 재시험했다. 둘 다 TCP 연결 단계에서
  약 5초 후 timeout, 경로는 기본 경로와 같은 `en0`였다. 비밀번호 인증이나
  원격 명령은 수행하지 않았다. 샌드박스 안의 `local_permissions/denied` 결과와
  구분한다. 이 관찰만으로 원격 ACG나 서버 장애를 확정하지 않는다.
- 지정 VPN 공개 도메인은 DNS 해석 성공, TCP 443은 연결 거절, TCP 8443은
  연결 성공이었다. 8443의 HTTPS 요청은 인증서 검사 우회 없이 HTTP 404를
  반환했다. 대조 대상 일반 HTTPS 443 연결도 성공했다. 이는 VPN 로그인·터널
  연결 성공 증거가 아니며, 이 결과만으로 Agent 등록 URL의 포트를 변경하지 않는다.

## 현재 확인된 결과

- 공식 1.1.4 설치본의 원본 서명과 Gatekeeper 공증 승인을 샌드박스 밖에서
  확인했다. 앱 ID는 `com.ncurity.ncurionsa`, 서명자는
  `N Curity Co.,Ltd. / RX8JGWX6RU`다. 샌드박스 안에서 나온 서명 서비스 오류를
  실제 파일 변조 판정으로 사용하지 않았다.
- Apple Silicon에서 x86_64 실행이 실패하고 Rosetta 설치 기록이 없어 공식
  Apple 도구로 Rosetta를 설치했다. 별도 에이전트의 새 프로세스에서 실제 Intel
  명령 실행, 설치 원본/앱 139개 파일 해시 일치, 설치 앱 서명과 실행 경로를 확인했다.
- `/Applications/NAVER Cloud SSL VPN.app`의 실제 등록 화면을 확인했고,
  사용자가 VPN을 연결했다. macOS 27에서의 이번 실행 성공이 공식 지원을
  추가하거나 모든 재접속의 호환성을 보장하는 것은 아니다.
- 이후 두 서버 모두 SSH TCP 연결 성공, 경로는 VPN `utun4`로 바뀌었다.
  이전 timeout의 직접 조건인 VPN 경로 부재를 확인했다. VPN 연결 전에는
  원격 ACG/서비스 상태를 특정할 수 없었다.
- 두 서버의 ED25519 호스트 키가 동일했고 기존 비교 키는 없었다. 사용자에게
  지문과 한계를 알린 뒤 명시적인 **최초 신뢰(TOFU)** 승인을 받아 비공개
  `known_hosts`에 고정했다. 운영진 키와 독립 대조한 것은 아니다. 이후 모든
  접속은 `StrictHostKeyChecking=yes`를 유지하며 키 변경을 자동 수락하지 않는다.
- 두 서버 모두 1회 비밀번호 인증과 계약 없는 읽기 전용 `preflight`가 성공했다.
  둘 다 Ubuntu 24.04/Python 3.12.3이며, GPU는 4 CPU·약 47GiB RAM·L4
  23034MiB·드라이버 580.159.04, 일반 서버는 2 CPU·약 8GiB RAM이다.
  시점별 프로세스/VRAM 표본과 서비스 배포·정상 가동 검증은 별개다.
- 이후 VPN 경로가 다시 없어져 두 서버가 `en0` 기본 경로에서 TCP timeout을
  보였다. 모델/데이터/학습 시험은 시작하지 않았고 재연결을 요청했다. 중단된
  의존성 dry-run의 원격 프로세스 상태를 먼저 확인하고 solver를 중복 실행하지 않는다.

## 다음 절차

1. 새 접속 환경에서는 공식 지원 OS 여부와 시험 설치 승인 범위를 확인한다.
   후자의 경우 설치본 출처·서명·아키텍처·의존성과 변경 범위를 먼저 확인한다.
   문서상 지원 밖인 OS를 정상 지원으로 표시하지 않는다.
2. 실제 Agent 실행·등록·OTP·연결을 확인한다. OTP는 일시적 인증값이므로
   접속 파일이나 진단 로그에 보관하지 않는다. 실제 사용 경로의 연결과 새
   프로세스에서의 확인 없이 설치 완료로 보고하지 않는다.
3. VPN IP와 사설 대상의 터널 경로를 확인한 다음 읽기 전용 진단을 실행한다.

   ```sh
   python -m deployment.ssh_diagnose --role all --output .cache/ssh-after-vpn.json
   ```

   `dev/`에서 Anaconda `py312`로 실행한다. 출력 파일은 새 이름이어야 한다.
   호스트 키는 신뢰 가능한 기준과 확인하고 기존 엄격한 검증을 유지한다.
4. 연결이 성립하면 서버명·OS·CPU/RAM·디스크·진행 중인 프로세스·GPU 상태를
   읽기 전용으로 조사한다. 이후 역할별 plan/preflight를 수행한다. 일반 서버의
   C 코드와 실제 ACK 계약을 임의로 대신 만들지 않는다.

매뉴얼 21쪽에 따라 드라이버·CUDA·방화벽·포트를 임의 변경하거나 서버를
재부팅하지 않는다. 사용자 지침에 따라 `rm`, 디스크 초기화 및 같은 파괴적
동작의 우회도 금지한다. 매뉴얼의 서버 반납·삭제 일정은 운영진 최신 공지와
확인하고, 실제 배포 데이터의 보존 범위를 별도로 확인한다.
