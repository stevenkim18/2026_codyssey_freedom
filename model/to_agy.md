## 3. 현재 문제: 데이터가 틀린 것이 아니라 표현 단위가 맞지 않음

다음 예시로 이해하세요.

```text
원문: 김가상에게 연락
정답 이름: 김가상
정답 문자 위치: [0, 3)   # 끝 3은 포함하지 않음

현재 B의 word splitter 결과:
  ["김가상에게", "연락"]

문제:
  GLiNER word span은 첫 단어 전체를 가리킬 수 있지만
  첫 단어 안의 "김가상"만 가리킬 수 없음.
```

기본 splitter 정규식은 `\w+(?:[-_]\w+)*|\S`입니다. 원문 정답이 정확해도 조사가 붙은 일부 단어의 정답 경계는 표현할 수 없습니다.

### 이미 실행한 전체 결과

| 분할 | 전체 문서 | 모든 정답 보존 가능 | 거절 | 가능한 고유 문장 |
|---|---:|---:|---:|---:|
| train | 243,711 | 2,635 | 241,076 | **2,615** |
| dev | 28,147 | 577 | 27,570 | 570 |
| test_track_a | 28,142 | 120 | 28,022 | 119 |

변환 가능한 train 부분에는 `KR_DRIVER_LICENSE`, `KR_PASSPORT`, `KR_NHIS`, `KR_VEHICLE_PLATE`, `USERNAME`, `PERSONAL_ATTRIBUTE`, `URL` 정답이 남지 않았습니다. 이 부분집합을 정식 학습 자료로 사용하면 안 됩니다.

현재 상태 코드는 **`blocked_compatibility`**, `training_ready=false`입니다. 검사 코드가 실패한 것이 아니라, 학습 준비 조건을 충족하지 못했다는 결과입니다.

상세 근거는 [변환 결과 JSON](reports/conversion-v1.json), [쉬운 결과 보고서](reports/conversion-summary.md), [실제 토크나이저·collator 검사](reports/conversion-runtime-v1.json)에 있습니다.

### 별도로 유지할 2단계의 발견

- 원본 전체의 파일 손상·정답 위치 불일치·분할 간 문장/템플릿 중복은 발견 0건입니다.
- 분할 내부 동일 문장 추가 등장은 train 3,286 + dev 302 + test 447 = 4,035건입니다. 중복 문장의 정답은 일치했습니다.
- 원본 dev·test에는 `PERSONAL_ATTRIBUTE` 정답이 0개입니다.
- 원본 모든 분할에 개인정보 없는 정상 문장이 0건입니다.
- 중복 처리는 원본을 보존하고 후속 표본 선정·평가 규칙에 명시해야 합니다.

## 4. 작업 A — 한국어 분할 호환성 해결안 만들기

**목표:** 원문만 보고 결정하는 분할 방식으로 정답 경계를 더 많이 표현할 수 있는지 검증하고, 학습과 B의 실제 추론에 공동 적용할 수 있는 안을 제시하세요.

### 수행 순서

1. 현재 방식과 작은 합성 사례의 실패를 재현합니다.
2. 기존 방식 + 한국어 분할 후보 1~2개부터 비교합니다. 형태소 기반 분할 등을 검토할 수 있지만 결과가 좋아질 것이라고 가정하지 마세요.
3. 후보는 **원문만 입력받아** `(token, original_start, original_end)`를 반환하게 만듭니다. gold 정답·BIO·템플릿·문서 ID를 분할 결정에 쓰지 마세요.
4. 후보 코드는 `model/` 안에 두고 기존 방식과 나란히 검사할 수 있게 합니다. B의 운영 코드를 먼저 바꾸지 마세요.
5. train/dev에서 표현 가능 수량과 유형별 보존율, 토큰·창 한도를 검사합니다. 시험셋으로 후보나 설정을 고르지 마세요.
6. 가능하면 train 전체를 진단하고 **고유 문서 5,000건 이상과 필요한 유형 분포**를 확보하는지 확인합니다. 개수만 채우고 유형 소실을 숨기지 마세요.
7. B가 재사용할 인터페이스·필요 패키지·사전 버전·위치 복원·전처리 버전·테스트를 문서로 제시합니다. 이후 공동 채택 전에는 운영 적용 완료라고 쓰지 마세요.

### 반드시 통과해야 할 조건

- 원문을 정규화하거나 정답 시작·끝을 조용히 바꾸지 않음
- 비공백 글자·이모지 ZWJ·결합 문자 누락 없음
- 같은 단어가 여러 번 나와도 정답의 실제 위치를 사용함
- 최대 384단어, 엔터티 최대 12단어, 라벨·특수 토큰 포함 최대 512 서브토큰 검사
- 길이 초과를 무음 잘라내기로 해결하지 않음
- 창 사이에 걸친 정답 일부를 정답 없는 정상 예시로 출력하지 않음
- 출력 정답을 원문 위치로 돌리면 종류·시작·끝이 원본과 정확히 일치함
- 모든 문서와 정답에 대해 출력/거절 개수의 합계가 원본과 일치함
- 학습과 실제 추론에서 같은 분할·원문 위치 복원 규칙을 사용하도록 설계함

기본 한도나 모델 구조를 바꿔야 한다면 별도 변경안으로 설명하세요. 현재 M0 전용 로더의 제약을 우회해 통과한 것으로 표시하지 마세요. 후보가 실패해도 수치·사유를 보고하고 작업 B를 계속할 수 있습니다.

## 5. 작업 B — 4단계 평가 시스템 구현

분할 문제 해결을 기다리지 않고 **합성 정답·예측 자료로** 구현할 수 있습니다. 모델을 실제로 호출하거나 학습한 결과를 꾸며 내지 마세요.

### B1. 문자 위치 기준 지표 계산

`model/evaluation/`에 평가 코드를 만들고 `model/tests/`에 테스트를 추가하세요. 아래 파일명은 제안이며 기존 코드와 충돌하지 않게 조정할 수 있습니다.

| 산출물 제안 | 기능 |
|---|---|
| `evaluation/metrics.py` | 정확한 종류·문자 위치 일치로 TP/FP/FN·정밀도·재현율·F1 계산 |
| `evaluation/records.py` | 실험 설정·지표·근거 개수의 저장 형식 검증 |
| `evaluation/compare.py` | 부모 실험·공통 기준과의 차이 및 비교 조건 확인 |
| `evaluation/service_cases.py` | 독립 시험셋의 수량·위치·중복·분포·버전 검사 |
| `evaluation/README.md` | 실행 명령·지표 정의·제한·실제 실행 여부 |

채점 단위는 `(document_id, type, start, end)`이며 문자 끝은 exclusive입니다. 종류와 두 위치가 모두 맞아야 TP입니다. 같은 문장이 다른 문서에 있으면 문서 단위를 구분합니다.

```text
precision = TP / (TP + FP)
recall    = TP / (TP + FN)
F1        = 2*TP / (2*TP + FP + FN)
```

- 각 식의 분모가 0이면 그 지표는 `null` 등 명시적 평가 불가로 저장합니다. 임의로 0%·100%를 넣지 마세요.
- 전체 micro 지표는 TP/FP/FN을 합쳐 계산합니다. macro 지표를 만들면 평균 대상·제외 유형을 명시합니다.
- 유형별 지표·정답 수·예측 수·미탐 수를 함께 남깁니다.
- 같은 위치의 다른 라벨은 구분합니다. 겹치는 정답이 있다는 이유만으로 하나를 삭제하지 마세요.
- 중복 정답·예측의 처리 규칙을 명시하고 테스트합니다. set 변환으로 중복을 조용히 지워 점수를 높이지 마세요.
- 공식 BIO 점수와 자체 문자 스팬 점수는 이름·계산 기준을 분리합니다.
- 중요 유형별 미탐·분모·변화·신뢰구간을 보고할 계산 방법도 문서화하고 검증합니다. 불확실성·표본 수를 숨기지 마세요.

사람이 손으로 답을 알 수 있는 사례부터 테스트하세요: 완전 일치, 누락, 오탐, 유형 불일치, 위치 한 글자 차이, 빈 정답/예측, Unicode, 같은 span의 두 유형, 중복, 문서 간 같은 위치.

### B2. 정책을 적용한 지표

정상 문장 오차단율은 단순 NER 오탐률과 다릅니다. B의 정책을 적용해 실제 차단 판단을 계산해야 합니다. [B 정책](../dev/gateway/policy.py), [마스킹·통제 엔진](../dev/gateway/engine.py), [비밀키 규칙](../dev/detector/rules.py)을 확인하고 기존 로직을 재사용하거나 명시적 어댑터를 주입하세요.

모델 단독과 동일 규칙 결합 결과를 분리합니다. 원문 재검사와 연결되는 마스킹 잔존율은 계산 계약·합성 테스트부터 준비하고 실제 모델 실측은 대기 상태로 남길 수 있습니다. 비밀키 규칙의 효과를 파인튜닝 성과로 기록하지 마세요.

### B3. 실험 기록과 공정 비교

[experiment-plan.json](configs/experiment-plan.json)의 `comparison_protocol_plan`, `experiment_record_plan`을 구현 기준으로 사용하세요. 최소 기록 항목은 다음과 같습니다.

- 실험 ID, 부모 실험 ID, 공통 기준 실험 ID, 변경 사항, 비교 모드
- 모델 revision 또는 체크포인트 SHA-256, 데이터 revision·분할·시험셋 버전
- 표본 목록 확인값, seed, 추론 설정
- 라벨·임계값·규칙·정책·문장 분할·겹침·후처리·채점 방식 버전
- 실행 시작·종료 시각(UTC), 전체·유형별 지표와 분모
- 중요 유형별 미탐·정답 수, 정상 문장 오차단·정상 문장 수
- 부모 실험 대비 차이, 공통 기준 대비 차이

비율은 `[0,1]`로 저장하고 `%p 차이 = 100 * (현재 비율 - 기준 비율)`로 계산합니다. 개수 차이를 %p로 표시하지 마세요. 비교할 수 없는 데이터·채점 조건이면 차이를 계산해 발표하지 말고 불일치 사유를 표시하세요.

M0·M1 모두 dev에서 같은 기록된 절차·탐색 범위·예산으로 설정을 선택합니다. 각자 선택한 설정의 차이는 전체 파이프라인 효과입니다. 추가 학습만의 효과를 주장하려면 다른 설정을 고정한 비교가 필요합니다.

누적 변경 A→B→C의 차이는 그 순서에서 추가한 효과입니다. 독립 효과로 해석하지 마세요. 필요할 때 공통 M0 기준에서 한 요소만 바꿔 비교하고, 모든 조합을 자동으로 실행하지 마세요.

### B4. 독립 서비스 시험셋 300건

학습 전에 고정할 별도의 합성 시험셋을 작성·검증하세요.

- 요청 150건 + 응답 150건 = 총 300건
- 개인정보 없는 정상 사례 100건 이상
- 중요 유형 `KR_RRN`, `KR_BANK_ACCOUNT`, `CREDIT_CARD`, `KR_PHONE_NUMBER`, `EMAIL_ADDRESS` 각각 정답 엔터티 30개 이상
- 표·JSON·코드·조사·긴 문서·혼합 언어·분할 경계 포함
- 공식 dev/test에 없는 `PERSONAL_ATTRIBUTE` 등 빠진 유형도 확인할 사례를 포함하도록 설계
- 한 문서에 여러 엔터티를 넣을 수 있지만 위치·종류는 정확해야 함
- 실제 개인정보·인증정보를 사용하지 않음
- 공식 데이터·학습용 자료와의 중복을 검사하고, ID·생성 방법·버전·확인값을 기록

300건을 의미 없는 템플릿 반복으로 채우지 마세요. 정답 검토가 필요한 사례를 표시하고, 검토 전에는 최종 동결 완료라고 쓰지 마세요. 동일한 고정 최종 시험셋을 dev 튜닝에 재사용하지 마세요. 조정용 합성 사례가 필요하면 별도 자료로 만들고 분리합니다.

원문이 들어 있는 JSONL은 기존 `.gitignore`에서 제외됩니다. 시험셋 전달·보존은 위치·확인값·재생성/배포 방법을 명시하세요. 파일을 Git에 넣으려고 전체 `*.jsonl` 제외 규칙을 해제하거나 강제로 대용량 자료를 추가하지 마세요.

## 6. 작업 C — 다른 데이터셋으로 보충할 수 있는지 검사

조사 후보는 [townboy/korean-pii-dataset](https://huggingface.co/datasets/townboy/korean-pii-dataset)입니다. 확인한 공개 카드에는 합성 문서 11,732건, 33개 유형, CC BY 4.0으로 표시되어 있습니다. **우리 저장소에서는 아직 다운로드·고정·품질·변환 가능 수량을 검증하지 않았습니다.** 후보이지 채택된 데이터가 아닙니다.

수행할 일:

1. 공식 출처에서 정확한 revision·라이선스·파일 목록을 고정합니다.
2. 원문 문자 스팬 구성(`raw`)을 검증합니다. 다른 모델의 BIO를 그대로 GLiNER 학습에 쓰지 마세요.
3. 33개 라벨을 프로젝트 18개 유형으로 연결할 표를 작성하고 애매한 매핑은 미확정으로 표시합니다.
4. 매핑 불가능한 정답을 지워 개인정보 있는 문장을 정상 예시로 바꾸지 마세요.
5. 현재 방식과 후보 방식별로 고유 학습 가능 수량·유형별 분포를 집계합니다. 수량 보충이 한국어 경계 문제까지 해결한다고 가정하지 마세요.
6. 원본 분할을 보존하고 기존 학습·dev·공식/독립 시험셋과의 중복을 검사합니다. 다른 데이터의 test를 학습에 섞지 마세요.
7. 도입 효과·한계·라이선스 고지·PRD 지정 데이터에 대한 추가/변경 내용을 보고합니다. 기존 K-PII-Bench를 조용히 교체하지 마세요.

순서는 A의 표현 문제를 먼저 파악한 뒤 보충 효과를 측정하는 것입니다. 후보가 도움이 안 되면 근거를 남기고 채택하지 않아도 됩니다.

## 8. 실행 환경과 원본 데이터 준비

같은 Mac이면 다음 경로를 먼저 확인해 재사용하세요.

```text
model/.cache/conversion-venv/                  # 실제 검증한 Mac CPU 전용 환경
model/.cache/k-pii-bench/844f92f7beba98fa964f957ba324017e82451701/data/
model/.cache/tokenizer/a0484667b22365f84929a935b5e50a51f71f159d/
model/.cache/conversion-v1/                    # 진단 예시·거절/역변환 기록
```

이 경로들은 Git에 없습니다. 다른 컴퓨터에서 clone하면 없는 것이 정상입니다. Mac arm64·Python 3.12라면 별도 가상환경에 해시 고정 목록으로 준비할 수 있습니다.

```bash
python3.12 -m venv model/.cache/conversion-venv
model/.cache/conversion-venv/bin/python -m pip --isolated install \
  --index-url https://pypi.org/simple --require-hashes \
  -r model/configs/conversion-macos.lock.txt

# 실제 학습 데이터 3파일, 총 약 1.56GB. 정상 캐시가 있으면 재사용합니다.
model/.cache/conversion-venv/bin/python -m model.data.download

# 토크나이저 약 4.3MB와 작은 설정 파일. 신경망 가중치가 아닙니다.
model/.cache/conversion-venv/bin/python -m model.data.prepare_tokenizer
```

다른 OS·아키텍처에 Mac lock을 강제하지 마세요. GPU 없는 기본 테스트는 아래처럼 Python 표준 라이브러리로도 실행할 수 있습니다. 환경 준비가 막히면 가능한 평가 코드와 합성 테스트를 계속 만들고 실제 runtime 검증 대기 항목을 남기세요.

```bash
python3 -m unittest discover -s model/tests -v
```

실제 tokenizer/processor와 전체 변환 검사는 [CONVERSION.md](data/CONVERSION.md)의 명령을 따르세요. 기존 `*-v1.json`을 덮어쓰지 말고 새 보고서 이름과 캐시 출력 폴더를 사용하세요. 후보별 실행에는 후보 ID·설정·패키지·사전 버전을 남기세요.

## 9. 작업 범위와 지켜야 할 조건

- 기본 편집 범위는 `model/`입니다. B/C 구현을 복제하거나 운영 설정을 조용히 바꾸지 마세요.
- GPU 서버 SSH·VPN 로그인, 드라이버·CUDA·서버 환경 변경, 모델 학습은 이번 인계 범위가 아닙니다.
- `.secrets`를 이 작업을 위해 읽을 필요가 없습니다. 값·키·OTP를 출력하거나 코드·문서·보고서에 복사하지 마세요.
- 실제 모델 가중치 다운로드·M0/M1 성능 실측은 이번 작업의 필수 조건이 아닙니다. 이를 위해 GPU 접속을 기다리며 평가 코드 개발을 멈추지 마세요.
- 원본 데이터·고정 기준·기존 보고서는 보존하세요. 파생 자료·새 후보·새 결과는 별도 버전으로 만듭니다.
- 테스트 실패를 정상 무탐지로 바꾸거나, 불완전 변환을 성공으로 표시하지 마세요.
- 실험한 내용과 앞으로 할 계획을 분리합니다. 합성 테스트 점수는 실제 모델 성능이 아닙니다.
- 자료·가중치·가상환경·첨부파일·비밀정보를 커밋하지 마세요. `git add .` 대신 변경 파일을 명시적으로 확인합니다.
- 커밋·푸시는 사용자의 요청 범위를 따릅니다. 이 인계서 작성 자체가 임의의 main/dev 머지나 원격 게시를 허용하는 것은 아닙니다.
- 패키지는 격리 환경에 설치하고 기존 전역·서버 환경을 보존합니다. 정확한 버전과 설치·실행 검증 범위를 기록합니다.

코드 변경은 PRD대로 **실패 테스트 → 최소 구현 → 정리** 순서로 진행합니다. GPU가 필요한 검증과 기본 오프라인 테스트를 구분하세요. 기본 테스트 통과 후에는 변경·실패·미해결 우려가 있을 때 필요한 추가 검증만 실행하세요.

## 11. GPU 접속 이후로 남길 작업

평가 실행기·학습 실행기의 코드를 추가로 준비할 수는 있지만, 다음은 실제 실행 전까지 완료로 표시하지 마세요.

- 서버의 실제 Python·패키지·CUDA·GPU 동작·메모리 확인
- 합의된 분할 방식과 라벨 설정으로 M0의 dev 기준선·설정 선택
- train에서 분야·유형·중복 기준을 기록한 5,000건 표본 선정
- batch 1부터 실제 추가 학습, epoch별 dev 평가·체크포인트 저장·재개 검증
