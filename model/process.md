# A 파트 작업 안내: 한국어 개인정보 탐지 모델 개선하기

이 문서는 AI 학습을 처음 접하는 사람도 작업의 목적과 순서를 이해할 수 있도록 쓴 안내서입니다. 기준은 [프로젝트 PRD](../docs/AI_PII_Gateway_PRD_v1.md)의 4·6·7·11·12절입니다. PRD의 요구사항과 이 문서에서 제안하는 구현 방법을 구분해 설명합니다.

**우리의 목표는 기존 모델에 한국어 예시를 추가로 공부시키고, 실제로 더 나아졌는지 같은 기준으로 비교한 뒤 B 담당자에게 전달하는 것입니다.**

## 1. 우리가 만들려는 것은 무엇인가요?

예를 들어 다음 문장이 있다고 생각해 봅시다. 이름과 이메일은 설명을 위해 만든 가상 정보입니다.

> 김가상의 이메일은 person@example.com입니다.

모델은 여기에서 다음 두 가지를 찾아야 합니다.

| 찾을 내용 | 분류 | 함께 알아야 할 것 |
|---|---|---|
| 김가상 | 사람 이름 | 문장에서 이름이 시작하고 끝나는 위치 |
| person@example.com | 이메일 주소 | 문장에서 이메일이 시작하고 끝나는 위치 |

단순히 “개인정보가 있는 문장이다”라고 판단하는 것으로는 부족합니다. **무슨 종류의 정보가 어느 위치에 있는지** 찾아야 B가 정확한 부분을 가릴 수 있습니다.

| 담당 | 하는 일 |
|---|---|
| **A — 우리** | 데이터 준비, 추가 학습, 성능 평가, 모델 전달 |
| **B** | 모델을 실제 서비스에서 실행하고, 탐지 결과에 따라 허용·가리기·차단 처리 |
| **C** | 처리 기록을 모으고 대시보드에 표시 |

A는 학습·평가용 프로그램을 만듭니다. 실제 서비스의 검사 서버와 대시보드는 각 담당자가 구현합니다. API 비밀키 탐지는 별도 규칙이므로, 개인정보 데이터로 학습한 모델의 성과와 나눠서 설명해야 합니다.

## 2. 전체 순서를 먼저 봅시다

**버전 고정 → 데이터 받기·검증 → 학습 형식 변환 → 평가 준비 → 기존 모델 측정 → 추가 학습 → 최종 비교 → B에게 전달**

| 단계 | 핵심 질문 | 완료되었을 때 남는 것 | 작업 장소 |
|---|---|---|---|
| ① 기준 고정 | 어떤 모델·데이터·도구를 썼나요? | 버전·라이선스·설정 기록 | 로컬 PC |
| ② 데이터 검증 | 문제와 정답이 올바른가요? | 검증 코드·검증 보고서 | 로컬 PC |
| ③ 학습 형식 변환 | 모델이 읽을 수 있는 형태인가요? | 변환 코드·변환 결과 | 로컬 PC에서 준비 가능 |
| ④ 평가 준비 | 좋아졌는지 어떻게 판단하나요? | 평가 코드·독립 시험셋 | 로컬 PC |
| ⑤ M0 측정 | 공부하기 전 실력은 어떤가요? | 기존 모델의 기준 성능표 | GPU 서버에서 실행 |
| ⑥ 추가 학습 | 한국어 예시를 공부시키면 어떻게 되나요? | 학습 기록·중간 저장본 | GPU 서버 |
| ⑦ 최종 비교 | 후보가 기존 모델보다 나은가요? | 비교 보고서·교체 판정 | GPU 서버에서 실행 |
| ⑧ 인계 | B가 같은 모델을 실행할 수 있나요? | 모델 패키지·사용 설명 | 서버와 로컬 PC |

코드 작성과 작은 예시를 이용한 테스트는 VPN 없이 진행할 수 있습니다. 공개 데이터 다운로드에는 인터넷 연결이 필요하지만, GPU 서버용 VPN은 필요하지 않습니다. 실제 GPU 실행은 접속 시간을 확보한 뒤 진행합니다.

## 3. ① 사용할 모델과 데이터 버전을 정합니다

### M0와 M1은 무엇인가요?

- **M0:** 추가 학습 전의 기존 모델. PRD에서 지정한 이름은 `urchade/gliner_multi_pii-v1`입니다.
- **M1:** M0를 한국어 데이터로 추가 학습한 후보 모델입니다.
- **학습 데이터:** PRD에서 지정한 `woohyun212/k-pii-bench`입니다. 개인정보 위치에 정답 표시가 붙은 합성 한국어 예시 모음입니다.

이번 작업은 이미 학습된 M0에서 출발합니다. 모델을 처음부터 새로 만드는 작업은 아닙니다.

### ‘리비전 고정’은 같은 판본을 사용한다는 뜻입니다

책으로 비유하면 책 제목만 적는 대신 “몇 년도에 나온 어느 판본인지”까지 기록하는 것입니다. 모델이나 데이터 제작자가 파일을 바꾸더라도 우리가 사용한 원본을 다시 받을 수 있게 합니다.

| 기록할 항목 | 이유 |
|---|---|
| 모델 이름과 리비전 | 같은 출발 모델을 다시 받기 위해 |
| 데이터 이름과 리비전 | 같은 문제·정답으로 다시 실험하기 위해 |
| Python·GLiNER·PyTorch 등 도구 버전 | 프로그램 동작 차이를 확인하기 위해 |
| 라이선스 사본·수정 이력 | 외부 자원 사용 조건과 변경 내용을 남기기 위해 |
| 표본 선택·학습에 사용한 설정과 난수 시드 | 어떤 예시를 뽑고 어떻게 실행했는지 재현하기 위해 |

난수 시드는 무작위 선택의 출발값입니다. 이를 기록하면 같은 방식으로 표본을 다시 뽑기 쉽습니다. 다만 시드만 같다고 모든 GPU 연산 결과가 완전히 같아지는 것은 아닙니다.

B 코드에는 M0 리비전 `1fcf13e85f4eef5394e1fcd406cf2ca9ea82351d`와 GLiNER `0.2.29`가 지정되어 있습니다. 1단계에서 같은 값을 기준으로 삼고, 데이터 리비전을 `844f92f7beba98fa964f957ba324017e82451701`로 고정했습니다. 모델의 기반 설정·토크나이저 버전도 함께 기록했습니다.

선정 결과는 [자산 기준](configs/assets.lock.json), [도구 계획](configs/toolchain-plan.json), [실험 계획](configs/experiment-plan.json), [출처·라이선스 기록](licenses/NOTICE.md)에 있습니다. 도구 버전은 설치 후보 기준이며, 서버에 실제로 설치된 전체 환경을 검증한 명세는 아닙니다. B의 버전과 다른 버전으로 바꾸려면 학습 형식과 인계 호환성을 먼저 확인합니다.

**완료 기준:** 사용한 모델·데이터·도구의 버전과 출처를 설명할 수 있습니다.

### 실험마다 ‘무엇을 바꿨는지’도 기록합니다

추가 학습 외에도 라벨의 이름·설명, 유형별 탐지 임계값, 같은 규칙의 결합, 긴 문장 분할·겹침, 탐지 위치 후처리가 결과에 영향을 줄 수 있습니다. 현재는 **개선 후보이며 효과를 측정하지 않았습니다.** 이미 B에 있는 기능은 함께 설정을 맞추고 재사용합니다.

실험에는 번호를 붙이고 바로 앞 실험과 공통 기준 실험을 연결합니다. ‘모델 버전 1에서 무엇을 바꿔 버전 2가 되었는지’를 추적하는 실험 일지입니다. 기록 항목은 [실험 계획](configs/experiment-plan.json)의 `experiment_record_plan`에 있으며, 실제 저장·비교 코드는 ④ 평가 단계에서 구현합니다.

## 4. ② 데이터를 내려받고 정답을 검사합니다

다운로드는 별도 학습 단계가 아니라, 데이터 검증을 시작하기 위한 준비입니다. 전체 데이터 크기와 저장 공간을 확인하고 고정한 리비전으로 받습니다. 다운로드한 원본·모델 가중치는 Git에 실수로 올라가지 않도록 제외 경로를 먼저 정합니다.

PRD에 적힌 데이터 규모는 총 300,000건입니다. 실제 받은 버전의 개수도 다시 확인합니다.

| 분할 이름 | PRD 기재 개수 | 용도 |
|---|---:|---|
| `train` | 243,711건 | 모델을 공부시키는 자료 |
| `dev` | 28,147건 | 학습 중 설정과 저장본을 고르는 자료 |
| `test_track_a` | 28,142건 | 최종 성능을 확인하는 시험 자료 |

### 정답이 틀리면 잘못 배웁니다

다음 문장에서 이름은 처음 세 글자입니다.

```text
김가상에게 연락해 주세요.
```

시작 위치를 0, 끝 위치를 3으로 표시하면 `김가상`을 뜻합니다. **시작 위치의 글자는 포함하고, 끝 위치의 글자는 포함하지 않습니다.** 이렇게 표시한 글자 구간을 ‘스팬(span)’이라고 부릅니다.

검증 프로그램은 다음을 검사합니다.

- 시작·끝 위치가 문장 범위를 벗어나지 않는지
- 표시된 위치의 글자가 정답 문자열과 일치하는지
- 같은 정답이 중복되어 있거나 서로 겹치는지 — 발견한 뒤 처리 기준을 확인합니다.
- 개인정보 종류별·분야별 예시가 얼마나 있는지
- 학습 자료와 시험 자료 사이에 같은 문장이나 템플릿이 겹치는지

템플릿은 “이름과 전화번호만 바꿔 여러 문장을 만드는 문장 틀”입니다. 같은 틀의 예시가 학습과 시험에 함께 들어가면, 새로운 상황을 잘 푸는지 평가하기 어려워집니다. 공식 템플릿 분리를 유지하고, 분할 간 템플릿 중복이 없는지 검사합니다.

문제가 발견되면 어떤 항목에서 몇 건이 발생했는지 보고합니다. 오류를 숨기거나 원본을 조용히 고치지 않습니다.

**완료 기준:** 정답 위치·분포·중복 검사 결과를 보고서로 확인할 수 있습니다. PRD의 T01에 해당합니다.

## 5. ③ 데이터를 모델이 읽을 수 있는 형태로 바꿉니다

사람이 보는 ‘글자 위치’와 모델이 학습하는 ‘토큰 위치’는 다를 수 있습니다. 토큰은 모델이 문장을 읽을 때 나누는 조각입니다. 토크나이저는 이 조각을 만드는 도구입니다.

따라서 검증한 원문 위치를 **고정한 GLiNER 버전이 요구하는 학습 형식**으로 변환해야 합니다. 데이터에 들어 있는 기존 BIO 표시는 그대로 학습에 사용하지 않습니다.

특히 다음 사례를 작은 테스트로 확인합니다.

- 이름 뒤의 조사: `김가상에게`에서 이름만 정확히 표시하는지
- 공백·줄바꿈·이모지·특수문자가 있을 때 위치가 유지되는지
- 긴 문장을 나눌 때 경계에 걸친 개인정보를 놓치지 않는지
- 모델이 처리할 수 있는 길이와 개인정보 구간 길이를 넘는 사례가 있는지

긴 문장을 프로그램이 알리지 않고 잘라 버리면 정답 일부가 사라집니다. 길이 제한에 걸리는 사례는 드러내고, 분할 또는 거절 기준을 정해 기록합니다.

‘라벨’은 개인정보 종류의 이름입니다. 예를 들어 프로젝트의 `PERSON`은 사람 이름을 뜻합니다. 데이터의 라벨과 모델에 전달할 이름·설명을 B와 맞추고 고정합니다.

**모델이 읽는 입력은 `text`입니다.** 개인정보 위치·종류는 정답으로 사용합니다. 답을 드러내는 `template_text`와 메타데이터는 학습 입력에서 제외합니다. 시험 문제 옆에 정답을 붙여 주지 않는다는 뜻입니다.

**완료 기준:** 원문과 정답의 연결이 유지된 학습 자료를 만들고, 경계 사례 테스트를 통과합니다.

### 3단계 실제 검사에서 확인한 제약

정확한 변환 코드와 테스트, 실제 GLiNER 토크나이저·학습 배치 검증은 구현했습니다. 그런데 현재 B의 단어 분할은 `김가상에게`를 한 단어로 읽어, 그 안의 이름 `김가상`만 단어 스팬으로 표현할 수 없습니다. **데이터 정답 위치는 맞아도 모델의 표현 단위와 맞지 않는 문제**입니다.

전체 문서를 실제 고정 토크나이저로 검사한 결과, 모든 정답을 보존할 수 있는 train 문서는 2,635건, 중복을 제외하면 2,615건입니다. PRD의 5,000건에 못 미치고 일부 유형도 남지 않았습니다. 정확히 변환할 수 없는 문서는 원본과 거절 기록을 보존했고, 부분 정답 자료나 가짜 정상 예시로 만들지 않았습니다.

현재는 **변환 도구 구현·진단 완료 / 학습 준비는 호환성 해결 대기** 상태입니다. A와 B가 정답을 보지 않고 원문만으로 결정되는 공통 한국어 분할·위치 복원 방법을 맞춘 뒤, 전체 변환과 M0 기준선을 같은 조건에서 확인해야 합니다. [상세 결과와 공동 확인 항목](reports/conversion-summary.md), [실행 방법](data/CONVERSION.md)을 참고하세요.

## 6. ④ 평가 코드와 독립 시험셋을 먼저 준비합니다

### 세 종류의 자료는 용도가 다릅니다

| 자료 | 학교 공부에 비유하면 | 사용 시점 |
|---|---|---|
| `train` | 공부하는 문제집 | 모델의 내부 값을 바꾸는 학습에 사용 |
| `dev` | 모의고사 | 학습 횟수·설정·후보를 고르는 데 사용 |
| `test` | 마지막 시험 | 선택이 끝난 모델의 최종 결과 확인에 사용 |

최종 시험 결과를 매번 보고 학습 방식을 바꾸면 그 시험에 맞춰 준비하게 됩니다. 그래서 **후보 선택은 dev로 하고, 시험셋은 최종 평가에만 사용합니다.** 데이터를 변형해 예시를 늘릴 때도 원본과 같은 분할에 둡니다.

### 독립 서비스 시험셋 300건을 학습 전에 고정합니다

공식 데이터 외에, 우리 서비스에서 실제로 만날 법한 합성 문장으로 별도의 시험 자료를 준비합니다. PRD의 조건은 다음과 같습니다.

- 요청 150건 + 응답 150건 = 총 300건
- 전체 중 개인정보가 없는 정상 사례 100건 이상
- 중요 유형 5개 각각에 대해 정답 엔터티 30개 이상
- 표·JSON·코드·조사·긴 문서·혼합 언어·분할 경계 사례 포함

엔터티는 이름 한 개, 전화번호 한 개처럼 찾으려는 정보 한 덩어리입니다. 한 문장에 여러 엔터티가 들어갈 수 있으므로, 문장 수와 엔터티 수는 다릅니다. PRD의 ‘정상 음성 사례’에서 음성은 소리 데이터가 아니라 **찾아야 할 개인정보가 없는 사례(negative)**를 뜻합니다.

중요 유형은 주민등록번호(`KR_RRN`), 계좌번호(`KR_BANK_ACCOUNT`), 신용카드번호(`CREDIT_CARD`), 전화번호(`KR_PHONE_NUMBER`), 이메일(`EMAIL_ADDRESS`)입니다.

### ‘정확도 몇 %’ 하나만 보면 부족합니다

개인정보가 아닌 글자가 훨씬 많으면, 아무것도 찾지 않는 모델도 전체 글자 기준으로 높은 점수를 받을 수 있습니다. 그래서 다음 지표를 함께 봅니다.

| 지표 | 쉬운 뜻 | 예시 |
|---|---|---|
| 정밀도 | 찾았다고 한 것 중 진짜 정답의 비율 | 8개를 찾았는데 6개가 맞으면 75% |
| 재현율 | 실제 정답 중 놓치지 않고 찾은 비율 | 실제 10개 중 6개를 찾으면 60% |
| F1 | 정밀도와 재현율을 함께 반영한 점수 | 위 예시에서는 약 66.7% |
| 미탐 | 정답이 있는데 놓친 경우 | 위 예시에서는 4개 |
| 오탐 | 정답이 아닌 것을 정답이라고 찾은 경우 | 위 예시에서는 2개 |
| 정상 문장 오차단율 | 정상 문장을 서비스가 잘못 차단한 비율 | 정상 100건 중 2건을 막으면 2% |

이 문서의 자체 문자 위치 평가 구현안은 **개인정보 종류와 시작·끝 위치가 모두 일치해야 정답**으로 세는 방식입니다. `김가상`이 정답인데 `김가상에게`까지 찾으면 완전히 맞힌 것으로 세지 않습니다. 최종 채점 규칙은 구현 전에 문서로 고정합니다.

공식 BIO 평가기를 사용할 때는 예측을 공식 정답 토큰에 맞춰야 합니다. 자체 문자 위치 점수와 공식 BIO 점수는 계산 기준이 다르므로 이름과 조건을 구분해 보고합니다.

오차단율은 탐지 결과에 **B와 같은 정책**을 적용해서 계산해야 합니다. 개인정보를 잘못 찾은 비율과 실제 차단한 비율은 다릅니다. 잘못된 마스킹도 별도로 확인합니다.

평가 코드가 맞는지는 사람이 직접 계산할 수 있는 작은 정답·예측 예시로 먼저 테스트합니다. 점수 계산을 검증하는 데 GPU는 필요하지 않습니다.

### 설정 변경과 추가 학습의 효과를 구분합니다

M1만 설정을 조정하고 기본 설정의 M0와 비교하면, 점수 차이가 추가 학습 때문인지 설정 때문인지 알기 어렵습니다. **M0와 M1 모두 dev에서 설정을 고르는 공정한 절차·탐색 범위·예산을 기록**합니다. 시험셋은 최종 검증용으로 남겨 둡니다.

실험별로 다음 항목을 기록하도록 평가 코드를 설계합니다.

| 기록 | 쉬운 설명 |
|---|---|
| 실험 ID·부모 ID·공통 기준 ID·변경 사항 | 어느 결과에서 출발해 무엇을 바꿨는지 |
| 모델·데이터 버전, 표본·시드 | 어떤 모델과 문제를 사용했는지 |
| 추론 설정, 라벨·임계값·규칙·정책·분할·후처리 버전 | 답을 찾고 처리하는 방법이 무엇이었는지 |
| 실행 시각·전체 및 유형별 정밀도·재현율·F1 | 언제 실행했고 어떤 종류를 얼마나 잘 찾았는지 |
| 중요 유형별 미탐·정답 수, 정상 문장 오차단·전체 정상 수 | 점수의 근거가 되는 실제 개수 |
| 직전 결과와 공통 기준 대비 변화 | 어떤 변경 뒤 얼마나 달라졌는지 |

예를 들어 재현율이 80%에서 83%가 되면 변화는 **3%p**입니다. 정답이 0개인 유형은 재현율을 0%나 100%로 정하지 않고 ‘평가 불가, 정답 0개’로 표시합니다. 현재 공식 dev·test의 `PERSONAL_ATTRIBUTE`가 해당합니다.

라벨을 바꾼 뒤 임계값도 바꾸는 식의 누적 실험에서 각 차이는 **그 순서에서 추가한 효과**입니다. 각 방법을 단독 적용했을 때의 효과와 같다고 단정하지 않습니다. 필요하면 공통 M0 기준에서 한 요소만 바꿔 비교하되, 모든 조합을 자동으로 실험하는 계획은 아닙니다.

**완료 기준:** 시험셋을 고정하고, 평가 계산 테스트를 통과합니다. 이후 실제 M0/M1 평가 결과가 PRD의 T02 증거가 됩니다.

## 7. ⑤ GPU 서버에서 기존 모델 M0의 실력을 측정합니다

먼저 VPN 연결과 SSH 접속이 필요합니다. SSH는 내 PC에서 서버의 터미널을 사용하는 접속 방법입니다. VPN 접속 인원이 제한되어 있으므로 팀원과 접속 시간을 맞춥니다.

선임 팀원은 `prd-a-py312` 환경에 Python 3.12.16, PyTorch 2.10.0, CUDA 런타임 13.0, cuDNN 9.18을 준비했다고 보고했습니다. **이 대화에서는 해당 학습 환경을 서버에 로그인해 직접 검증하지 못했습니다.** 접속이 가능해지면 기존 환경부터 확인하고 필요한 학습 패키지를 조사합니다.

| 확인 대상 | 확인하는 이유 |
|---|---|
| 현재 GPU 사용 작업 | B의 검사 서비스나 다른 팀원 작업과 겹치지 않기 위해 |
| GPU 인식·작은 연산·역전파 | 학습에 필요한 계산이 실제로 동작하는지 확인하기 위해 |
| 기존 Python 환경과 패키지 버전 | 선임 팀원이 준비한 환경을 정확히 사용하기 위해 |
| 모델·토크나이저 파일과 리비전 | 이미 받은 자산을 확인하고 중복 다운로드를 줄이기 위해 |
| 저장 공간 | 모델 저장본과 데이터를 보관할 공간이 있는지 확인하기 위해 |

M0 가중치가 없다면 이 단계 전에 고정 리비전으로 받습니다. 가중치는 학습된 모델의 내부 숫자들이 들어 있는 파일입니다. 변환 작업에 필요한 설정·토크나이저는 이보다 앞서 받을 수 있습니다.

먼저 작은 합성 예시로 실행을 확인한 뒤 dev에서 기준 성능을 측정하고 오류 유형을 살펴봅니다. 최종 비교용 시험셋은 학습 설정을 고르는 데 사용하지 않습니다. 나중에 M0와 M1을 같은 시험셋에서 최종 평가합니다.

학습 전에는 필수 라벨·문장 분할·원문 위치 처리를 B의 실제 실행 방식과 맞춥니다. M0 기본 설정과 dev에서 조정한 설정의 결과를 서로 다른 실험으로 남긴 뒤 추가 학습으로 넘어갑니다. 세부 개선 후보의 효과는 이후 실험으로 확인합니다.

**완료 기준:** M0의 실행 조건·유형별 성능·오류 사례를 재현할 수 있습니다. 원본 M0는 따로 보존합니다.

## 8. ⑥ 소규모 추가 학습을 시작합니다

### 처음부터 전체 자료를 넣지 않습니다

PRD는 train에서 분야와 개인정보 종류를 고려해 **5,000건으로 먼저 시험 학습**하도록 정합니다. 전체 실행이 올바른지 확인한 뒤 필요하면 10,000건 이상으로 확대합니다. 선택한 예시 목록과 선택 방법을 남깁니다.

| 용어 | 쉬운 뜻 | PRD의 시작 기준 |
|---|---|---|
| epoch | 선택한 학습 자료 전체를 한 번 공부하는 것 | 초기 탐색 1~3회 |
| batch | 한 번에 계산하는 예시의 묶음 | 1건부터 메모리 측정 |
| 학습률 | 한 번 배울 때 내부 값을 바꾸는 크기 | `1e-5~5e-5`, 즉 `0.00001~0.00005` |
| gradient accumulation | 작은 묶음의 계산 결과를 여러 번 모아 한 번 반영하는 방법 | 메모리를 측정하며 조정 |
| 체크포인트 | 학습 중간의 모델 저장본 | 설정·평가 결과와 연결해 저장 |
| 임계값 | 모델의 탐지 점수가 이 값 이상일 때 탐지로 채택하는 기준 | dev 결과로 선택 |

임계값을 낮추면 더 많이 찾는 대신 오탐이 늘 수 있습니다. 모델 점수 0.8을 “정답일 확률이 정확히 80%”라고 단정하지 않습니다.

학습 프로그램은 모델과 데이터를 불러오고, 학습하면서 dev 성능을 측정하고, 중간 저장본과 설정·걸린 시간·GPU 메모리 사용량을 남기도록 만듭니다. 재시작에 필요한 정보도 저장할 수 있도록 설계합니다.

epoch별 dev 결과를 해당 체크포인트와 연결하고, 어떤 저장본을 왜 골랐는지도 실험 이력에 남깁니다. 최종 시험셋을 매 epoch 평가해 저장본을 고르지 않습니다.

‘학습 손실(loss)’은 학습 중 틀린 정도를 계산한 값입니다. 손실이 줄었다고 새로운 문장도 반드시 잘 찾는 것은 아닙니다. **후보 선택은 dev의 탐지 성능으로 판단합니다.**

공부한 예시는 잘 풀지만 새 예시는 더 못 풀면 ‘과적합’이라고 합니다. 더 오래 학습한다고 항상 좋아지지는 않습니다. dev 성능이 개선되지 않으면 원인을 확인하고, 실행 전에 정한 중단 기준에 따라 학습을 끝냅니다. 무한히 epoch를 늘리는 방식으로 진행하지 않습니다.

**완료 기준:** 학습 실행 코드가 작은 실제 실행을 통과하고, 설정·dev 평가·저장본이 연결된 후보 M1을 얻습니다. 성능 향상 여부는 다음 단계에서 판정합니다.

## 9. ⑦ M0와 M1을 최종 비교합니다

dev로 체크포인트·임계값 선택을 마친 후, 공식 시험셋과 독립 서비스 시험셋으로 최종 평가합니다. 같은 데이터·채점 방식·추론 환경을 사용하고, 각 모델의 dev 선택 설정을 기록합니다. 시험 결과를 보고 유리하게 설정을 다시 고르지 않습니다.

**모델만 사용한 결과와, 동일한 탐지 규칙을 결합한 결과를 각각 보고합니다.** 규칙을 바꿔 얻은 개선을 모델 학습의 성과로 혼동하지 않기 위해서입니다.

선택이 끝난 모델·설정을 최종 시험셋에서 평가하고 실험 이력 비교표를 만듭니다. 각자 dev로 고른 설정의 비교는 전체 처리 방식의 차이를 보여줍니다. **추가 학습만의 효과를 주장할 때는 라벨·임계값·규칙·문장 분할·후처리 등 다른 조건을 고정한 비교가 필요**합니다. 조건이 달라진 결과에는 변경 사항을 함께 표시합니다.

| PRD의 교체 기준 | 쉬운 설명 |
|---|---|
| 중요 유형 합산 재현율이 M0 이상 | 중요한 정보를 놓치는 정도가 전체적으로 더 나빠지지 않아야 합니다. |
| 전체 엔터티 F1이 M0 이상 | 전체 탐지 성능도 더 나빠지지 않아야 합니다. |
| 정상 문장 오차단율 증가가 1%p 이하 | 예를 들어 M0가 2%라면 M1은 3% 이하여야 합니다. |
| 중요 유형별 퇴행 검토 | 평균이 좋아도 계좌번호만 더 못 찾는다면 원인 해결 전 교체를 보류합니다. |
| 운영 지연·메모리·통합 테스트 통과 | 점수가 좋아도 실제 서비스에서 감당할 수 있어야 합니다. 이 부분은 B와 함께 검증합니다. |

중요 유형별로 정답 개수, 미탐 개수, M0 대비 변화와 신뢰구간을 보고합니다. 신뢰구간은 제한된 예시로 계산한 수치에 어느 정도 불확실성이 있는지 보여주는 범위입니다. 표본이 적다는 한계도 함께 적습니다.

마스킹 정책까지 적용한 평가에서는 가린 뒤에도 개인정보가 남는지 확인하는 ‘잔존율’도 다룹니다. 채점 대상과 계산 방법은 B의 정책·재검사 동작과 맞춥니다.

**기준을 통과하면 교체 후보가 됩니다. 통과하지 못하면 M0를 유지하고, 무엇이 나빠졌는지 기록합니다.** 평가 코드는 좋아졌는지 판정해야 하며, “학습했으니 반드시 개선된다”는 가정으로 만들지 않습니다.

## 10. ⑧ B가 실행할 수 있는 모델 패키지를 전달합니다

가중치 파일 하나만 전달하면 라벨·토크나이저·설정이 달라 같은 결과가 나오지 않을 수 있습니다. 모델 패키지는 다음을 함께 묶은 전달물입니다.

- 모델 가중치, 모델 설정, 토크나이저
- 라벨 매핑, 탐지 임계값, 전처리 방법
- 모델·임계값·도구 버전, 원본 모델·데이터 리비전
- 파일별 SHA-256, 라이선스·수정 이력
- 평가 결과, 알려진 한계, 재현 방법
- 최종 실행 설정, 실험별 변경 이력과 공통 기준 대비 개선 비교표
- 다시 문제가 생겼는지 확인할 수 있는 합성 회귀 사례

SHA-256은 파일 내용으로 계산한 긴 확인값입니다. 전달한 파일이 같은 파일인지, 전송 과정에서 바뀌지 않았는지 비교하는 데 사용합니다. 회귀 사례는 수정이나 교체 후 예전에 맞히던 사례를 다시 틀리지 않는지 확인하는 예시입니다.

B의 현재 패키지 명세와 M0 로더를 확인하고, **추가 학습한 M1의 출처 표시·로딩·평가 승인 조건을 B와 합의**해야 합니다. 기존 M0 패키지 형식에 파일만 넣으면 M1 인수가 끝나는 것으로 간주하지 않습니다.

B가 로딩·원문 위치·성능·교체 실패 복구를 검증합니다. A의 평가 보고서가 통과한 것과 실제 서비스 교체가 완료된 것은 별개입니다. 이것이 PRD의 G2 후보 인수 단계입니다.

**완료 기준:** B가 전달물을 검증하고 같은 후보 모델을 실행할 수 있으며, 적용 여부와 미해결 항목이 기록되어 있습니다.

## 11. 코드는 어떤 순서로 만드나요?

PRD는 ‘실패하는 테스트 → 최소 구현 → 정리’ 순서로 개발하도록 정합니다. 예를 들어 정답 위치가 문장 밖으로 벗어나는 예시를 먼저 만들고, 검증 프로그램이 이를 제대로 거절하는지 확인합니다.

| 구현 순서 | 만들 프로그램 | 먼저 확인할 테스트 |
|---|---|---|
| 1 | 자산·설정 기록과 데이터 검증 | 잘못된 위치·라벨·중복을 드러내는지 |
| 2 | 학습 자료 변환 | 조사·공백·이모지와 분할 경계의 위치가 맞는지 |
| 3 | 평가 지표 계산·시험셋 조건 검사 | 손으로 계산한 정답·예측 결과와 점수가 같은지 |
| 4 | M0 평가 실행기 | 예측·버전·채점 결과가 올바르게 연결되는지 |
| 5 | 학습 실행기 | 작은 실행의 설정·저장·dev 평가가 연결되는지 |
| 6 | 비교 보고서·패키지 생성 | 교체 기준 미달을 드러내고 필요한 파일·기록이 있는지 |

기본 테스트는 작은 합성 자료로 실행해 GPU 없이도 데이터 처리·채점을 확인합니다. 실제 모델 로딩·학습·성능은 별도의 GPU 검증으로 확인합니다. 작은 테스트가 통과했다고 실제 학습까지 성공했다고 표시하지 않습니다.

아래 폴더 구성은 이 문서의 제안입니다. PRD의 A 담당 `training/`, `evaluation/` 역할을 현재 작업 위치인 `model/` 아래에 배치합니다. 아직 이 프로그램들이 구현되었다는 뜻은 아닙니다.

```text
model/
├── process.md       # 이 작업 안내서
├── configs/         # 자산 버전·라벨·학습 설정
├── data/            # 검증·변환 코드. 원본 데이터 저장 위치는 따로 지정
├── evaluation/      # 지표 계산·모델 평가·비교 보고서 코드
├── training/        # 추가 학습·중간 저장본 관리 코드
├── tests/           # 작은 합성 자료를 이용한 테스트
└── README.md        # 실제 설치·실행·재현 방법
```

큰 데이터·가중치·학습 결과의 저장 경로는 코드 경로와 구분하고 Git 제외 여부를 확인합니다. 로그인 비밀번호와 OTP는 코드·문서·학습 기록에 넣지 않습니다.
