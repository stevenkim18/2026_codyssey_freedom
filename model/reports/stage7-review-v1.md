- M0/M1의 서비스·dev 레코드 4개는 스키마 검사에 통과했고, 각각 대응하는 score JSON의 TP/FP/FN 및 유형별 지표와 일치했습니다. dev 유형별 gold 수는 원본 감사 보고서와 일치했습니다.

이 확인은 **현재 결과 파일의 내부 일관성**을 뒷받침합니다. GPU에 접속하거나 학습을 재실행하지 않았으므로 실제 체크포인트·서버 실행 설정까지 확인한 것은 아닙니다. 검증 수치와 입력 파일 SHA-256은 [검사 기록](stage7-review-checks-v1.json)에 있습니다.

## 3. 우선 해결할 문제

### P1 — 학습에 쓴 분할기가 실제 추론에 연결되지 않았습니다

근거: [학습 실행기](../training/run_stage6_m1.py)의 `prepare_5k_sample` 및 `main`, [분할 제안서](../segmentation/README.md) §4.2, [B backend](../../dev/detector/gliner_backend.py)의 `_tokens`·`_inspect`.

학습 예시는 `ko_atomic_suffix_v3`로 만들지만, 제출된 M1 평가 코드는 `GLiNER.from_pretrained(...)` 후 일반 `GLiNERBackend`를 생성합니다. 사용자 분할기를 모델의 `data_processor.words_splitter`에 연결하는 코드가 없습니다. GLiNER는 실제 예측 입력도 이 속성으로 나눕니다. 학습된 가중치를 저장하는 것만으로 Python 분할 함수가 함께 저장·재적용되지는 않습니다.

또한 제안서처럼 backend의 `_tokens`만 바꾸면 창 계획만 바뀌고 `predict_entities` 내부의 분할은 그대로 남습니다. 계획·실제 예측·문자 위치 복원이 같은 분할기를 쓰도록 연결해야 합니다.

**필요 작업:** B와 공통 어댑터·버전을 합의하고, 새 프로세스에서 체크포인트를 다시 불러온 뒤 조사·URL·긴 문서 경계의 실제 예측 경로까지 검증합니다. 같은 채택 분할·라벨·임계값·규칙 조건에서 M0/M1을 비교합니다. 원래 M0 결과는 역사적 기준선으로 보존합니다. 서버에서 별도 패치를 썼다면 실행 당시 소스·설정·해시를 먼저 회수해 제출 코드와 맞춰야 합니다.

### P1 — 미완료 검사가 정상적인 빈 예측으로 채점됩니다

근거: [M0 실행기](../evaluation/evaluate_m0.py) `run_inference` 47행 부근, [M1 실행기](../training/run_stage6_m1.py) `run_inference` 196행 부근.

두 실행기 모두 `backend.inspect`의 `status`를 확인하지 않고 `findings`만 가져옵니다. B backend는 창 계획을 완료하지 못하면 `status="incomplete"`를 반환할 수 있습니다. 이 상태의 빈 findings가 지금은 “검사를 끝냈지만 아무것도 찾지 않음”으로 바뀝니다. 정상 문서에서는 오차단율을 유리하게 왜곡할 수도 있습니다.

각 실행기의 실제 함수 본문을 추출해 `status="incomplete", findings=[]`를 반환하는 합성 backend로 호출했습니다. **두 함수 모두 오류 없이 빈 예측을 받아들였습니다.** 기존 173개 테스트가 통과해도 이 결함은 남습니다. 기존 실행에서 실제로 몇 건이 미완료였는지는 저장된 집계만으로 알 수 없습니다.

**필요 작업:** 모든 문서의 complete/incomplete/error를 보존하고, complete가 아닌 문서를 빈 탐지로 처리하지 않습니다. 미완료가 있으면 유효한 최종 평가로 승인하지 않고 실패 개수·원인을 보고합니다. 회귀 테스트와 수정 후 재평가가 필요합니다.

### P1 — 독립 서비스 시험셋이 전수 미검토·미동결입니다

근거: [서비스 manifest](../evaluation/service-test-v1.manifest.json)에서 `unreviewed_documents=300`, `status=draft_needs_review`, `frozen=false`입니다. 실제 로컬 JSONL의 해시는 manifest와 같고, 로컬 검증도 미검토 300건으로 재현됐습니다.

수량·문자 위치 검사를 통과한 초안과 사람이 정답 의미까지 확인해 동결한 시험셋은 다릅니다. 이미 본 300건으로 임계값·분할·학습 방식을 고른 뒤 같은 자료를 독립 최종 성능 증거로 사용할 수 없습니다.

**필요 작업:** 기존 v1은 탐색/회귀 자료로 보존합니다. 보완 과정의 설정 선택은 dev와 별도의 정상 문서 조정용 자료로 합니다. 새 최종 서비스 holdout은 미리 작성하고 사람이 정답을 검토해 동결하며, 설정 선택에 사용하지 않습니다. 검토자를 기록하고 실제 검토 없이 `reviewed=true`만 채우지 않습니다. 아직 최종 성능 측정 결과가 없는 공식 `test_track_a`도 설정 선택이 끝난 후 평가합니다.

### P1 — epoch별 dev 평가와 후보 선택 근거가 없습니다

근거: [학습 실행기](../training/run_stage6_m1.py) 141~172행 및 `main`의 서비스 → dev 실행 순서, [실험 계획](../configs/experiment-plan.json)의 `epoch_history`.

제출된 Trainer에는 `eval_dataset`·epoch별 평가·최고 체크포인트 선택 설정이 없습니다. 2 epoch 후 마지막 모델을 저장하고 서비스 시험부터 평가한 다음 dev를 평가합니다. 이 흐름은 “dev에서 저장본과 임계값을 고른 뒤 최종 시험”이라는 완료 기준과 다릅니다.

**필요 작업:** 서버의 epoch 1·2 저장본, `trainer_state.json`, 실제 인자와 로그를 먼저 회수합니다. 저장본이 있으면 추가 학습 없이 dev에서 평가·선택할 수 있습니다. 없거나 학습 설정을 확인할 수 없다면 재현 가능한 새 실험이 필요합니다. M0/M1의 임계값 선택에도 같은 기록된 탐색 절차·예산을 적용합니다. 개인정보 없는 조정 자료는 최종 서비스 시험과 분리합니다.

**현재 자료만으로 과적합이나 추가 epoch 필요 여부는 판단할 수 없습니다.** loss 감소만으로는 새 문장에 대한 성능을 알 수 없습니다.

### P1 — 교체 실패를 패키징 단계의 임계값 조정만으로 해결한다고 가정합니다

근거: [현재 종합 보고서](m1-training-summary.md) §4.2, [후속 인계서](../to_codex.md) §3.

저장된 결과는 오차단 +7%p로 실패했고 계좌·카드 재현율도 하락했습니다. 임계값을 올리면 오탐과 함께 정탐도 줄 수 있습니다. “0.65~0.7이면 즉시 1% 이하”라는 주장은 측정 근거가 없습니다.

보고서의 “규칙을 결합하면 오탐이 자동으로 차단됨”도 현재 정책과 맞지 않습니다. [정책 어댑터](../evaluation/policy_metrics.py)는 모델 findings에 규칙 findings를 더하고, [B 정책](../../dev/gateway/policy.py)은 차단 유형을 발견하면 차단합니다. 모델 오탐을 자동 삭제하는 검증 필터가 아닙니다.

**필요 작업:** 7.5단계에서 dev 기반 보정과 오류 분석을 수행합니다. 오차단과 중요 유형 재현율을 함께 확인하고, 모델 단독/동일 규칙 결합 결과를 분리합니다. 허용 기준을 달성하지 못하면 M0 유지 결론으로 마무리할 수 있습니다. M1 채택이 보고서 작성의 필수 조건은 아닙니다.

## 4. 재현성과 문서 수정 항목

| 항목 | 확인된 차이 또는 누락 | 보완 방법 |
|---|---|---|
| 학습 설정 | 보고서: batch 4·누적 2·LR 2e-5·warmup 100. 코드: batch 8·누적 1·LR 3e-5·warmup ratio 0.1 | 서버의 실제 TrainingArguments와 소스 해시로 확정. 보고서·실행 코드를 일치시킴 |
| 표본 추출 | `random.seed(42)` 이후 난수를 쓰지 않고 변환 성공한 앞 5,000문서에서 중단. 분야·유형 고려 및 중복 제거가 없음 | 원본 ID·분야·유형·고유 문서 수·거절 사유를 기록하고 PRD 표본 선정 방식을 구현. 전량 후보의 18종 보존이 표본의 18종 보존을 보장하지 않음 |
| 캐시 재사용 | 5k 캐시 존재 시 해시 파일의 문자열을 그대로 반환. 모델도 config 파일 존재만으로 재학습을 생략 | 원본/변환 자료 해시와 실험 설정·체크포인트 해시를 검증한 뒤 재사용 |
| 모델 식별 | M1 레코드의 revision/SHA 필드 값이 실제 SHA가 아닌 `m1-ko-atomic-5k-v1` 이름 | 가중치·config·tokenizer·소스의 실제 확인값과 저장본 ID 기록 |
| 비교 재현 | M1 실행기는 `comparison_condition_id=m1-fine-tuned-5k`를 생성하지만 저장된 서비스 레코드는 `m0-baseline`. 현재 코드를 그대로 실행하면 M0와 비교 조건 ID가 달라 `not_comparable` | 비교 조건의 정의와 공통 ID 생성 절차를 코드에 반영하고 변경 이력 기록. ID를 같게 만드는 것만으로 공정성이 증명되지는 않음 |
| B 인수 상태 | M1 실행기 326행에서 `runtime_acceptance=True`를 고정 전달. 실제 B 인수 증거가 없음 | 확인 전에는 미확정으로 유지. 현재 reject는 이 값 때문에 바뀌지 않지만 이후 잘못된 replace를 방지해야 함 |
| 평가 근거 | M1 실행기는 문서별 예측·상태를 파일로 저장하지 않음. 로컬에는 M0 서비스 예측만 있음 | 모델/설정/자료 해시와 연결된 문서별 예측·상태를 접근 제한된 Git 제외 경로에 보존. 원문 없이도 재채점·문서 단위 paired bootstrap이 가능한 증거 확보 |
| 최종 평가 범위 | 공식 `test_track_a` 성능 결과, 동일 규칙 결합, 마스킹 잔존율, 실제 CI 출력이 없음 | dev 선택 완료 후 최종 평가에 포함. CI 계산 함수가 존재하는 것과 실제 결과에 CI를 보고하는 것을 구분 |
| 운영 성능 | 전체 처리 시간/문서 수만 있고 p95·메모리·마스킹 재검사 포함 통합 실측은 없음. 인계서의 30ms·4GB는 PRD §10의 p95 500ms 목표와 다름 | B와 실제 수용 기준을 확인하고 측정. 평균 처리 시간을 p95로 간주하지 않음 |

수치 서술 오류도 수정해야 합니다.

- 종합 보고서의 중요 유형 micro F1은 **57.51% → 58.06% 개선**이 아니라 score JSON 기준 **59.49% → 58.06%, −1.43%p**입니다.
- dev 주민번호 M0 TP는 **1,673**이 아니라 **1,354**입니다. M1 4,379와의 차이는 **+3,025건**입니다.
- dev 운전면허증 M0 TP도 **584건**입니다. M1 TP 584건을 “0에서 신규 탐지”라고 쓸 수 없습니다.
- M0 요약의 NRP·ORGANIZATION·PERSON·URL·USERNAME 행은 해당 JSON 및 원본 gold 수와 다릅니다. 예를 들어 PERSON gold는 요약의 26,052가 아닌 43,732입니다. 표는 JSON에서 자동 생성하는 편이 안전합니다.
- 원본 데이터에 정상 문서가 없다는 사실은 확인됐지만, 그것이 이번 오차단 증가의 유일한 원인이라는 것은 아직 가설입니다.
- `experiment-plan.json`은 여전히 `not_executed`, 표본 미선정 등의 상태를 담고 있습니다. 계획과 실제 실행 이력을 구분해 동기화해야 합니다.

## 5. 7.5단계 실행 순서와 완료 기준

| 순서 | 해야 할 일 | 완료 증거 | GPU 필요 |
|---|---|---|---|
| 1 | 현재 실험과 서버 산출물 보존·확인 | 실행 소스, 환경, TrainingArguments, 표본 ID/분포/해시, epoch 로그, 체크포인트 해시 | 파일 회수·확인부터 가능 |
| 2 | 평가 상태 처리, 공통 분할, 비교 ID, 캐시 검증 수정 | 실패 재현 → 수정 후 통과, 재로딩 후 동일 분할·위치 검증 | 기본 회귀는 로컬; 실제 모델 검증은 GPU |
| 3 | 분야·유형·중복을 고려한 표본 확인/보완 | 고유 5k 및 유형/분야 분포, train-only 출처 증거 | 선정은 로컬 가능 |
| 4 | dev로 저장본·임계값 선택 | M0/M1 동일 선택 절차, epoch별 dev 표, 별도 정상 조정 자료, 선택 이유 | 필요 |
| 5 | 오차단·계좌·카드 퇴행 원인 분석 | 문서별 오류 분류, 임계값/재학습 여부를 정한 근거 | 재추론·재학습을 할 때 필요 |
| 6 | 최종 시험 준비·평가 | 새 서비스 holdout 사전 검토·동결, 공식 test 및 서비스의 완결된 예측/정책 지표/CI | 검토는 사람; 추론은 GPU |
| 7 | 보수적인 최종 판정·문서 동기화 | replace/hold/reject 근거, M0 유지 여부, B 인수 대기 상태 명시 | 집계는 로컬 가능 |

계획은 **무조건 epoch 추가**가 아닙니다. 기존 저장본의 회수·평가로 해결할 수 있는 부분부터 확인하고, 재학습이 필요한 경우에만 새 실험을 만듭니다. 미검토 시험셋의 라벨을 사람이 검토하는 일과 B의 채택·인수 확인은 모델이 대신 완료 표시할 수 없습니다.

## 6. 보완 후 보고서·그래프 작성 기준

평가의 신뢰성과 실행 이력이 정리되면, M1의 채택 여부와 관계없이 `model/report_v1.md`를 작성할 수 있습니다. 실패 원인과 M0 유지 결정도 유효한 결과입니다.

| 그래프 | 필요한 원자료·주의점 |
|---|---|
| M0/M1 전체 정밀도·재현율·F1 | 검증된 최종 score JSON. dev와 final을 별도 패널로 표시 |
| 18종 재현율·F1 및 gold 수 | 유형별 TP/FP/FN. gold 0은 평가 불가로 표시 |
| 중요 유형별 미탐·재현율 변화 | 분모·CI·퇴행을 함께 표시 |
| 정상 오차단율과 허용 한도 | 실제 정책 판단·정상 문서 수·CI. 절대 %와 변화 %p 구분 |
| epoch별 loss·dev 성능 | 실제 Trainer 로그와 저장본별 dev 측정. 시작/끝 loss 두 값으로 곡선을 만들지 않음 |
| 임계값별 정탐·오탐 절충 | dev/별도 조정용 정상 문서에서 측정한 탐색 이력 |
| 분야·유형별 학습 표본 분포 | 실제 선택된 5k의 manifest. 전체 데이터 분포와 구분 |
| 분할 후보별 변환 가능량·유형 보존 | 기존 진단 보고서. 모델 탐지 성능 향상과 구분 |
| 지연 분포·p50/p95·메모리 | 요청별 실측과 자원 기록. 총 시간만으로 분포를 만들어내지 않음 |
| 오류 유형·형식·방향별 분석 | 문서별 예측·정답·검사 상태와 검토 결과 |

측정하지 않은 항목은 미측정으로 남깁니다. 보고서에는 문제·목표, 고정 자산과 라이선스, 직접 구현 내용/외부 자원/AI 활용, 학습·선택 절차, 비교 조건, 수치와 불확실성, 실패·제한, 교체 판정과 재현 방법을 연결합니다.
