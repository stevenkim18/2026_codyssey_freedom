## 1. 문제 배경과 핵심 원인

- **원인**: 데이터 오류가 아닌 **표현 단위(Representation Unit)의 불일치**.
  - 기본 GLiNER 공백 분할기 정규식(`\w+(?:[-_]\w+)*|\S`)은 `김가상에게`를 단일 단어(`["김가상에게"]`)로 분할합니다.
  - GLiNER의 출력 구조는 단어 단위 span 인덱스(`[first_word_idx, last_word_idx, label]`)이므로, 단어 내부의 일부 글자(`[0, 3)` = `김가상`)만을 가리킬 수 없습니다.
  - `010-1234-5678로`, `192.168.1.1에서`, `PM6465889의`와 같이 한글 조사/접미사가 붙은 PII 엔터티 경계가 기본 분할과 맞지 않아 표현 불가(`unaligned_entity_boundary`) 처리됩니다.
  - 긴 URL이나 이메일의 경우, 기본 단어 분할기가 기호마다 단어를 잘게 쪼개어 M0의 최대 스팬 폭(`max_width=12`)을 초과(`entity_exceeds_max_width`)하여 문서 전체가 거절됩니다.

## 2. 해결 원칙 및 필수 준수 규칙

1. **원문만 보고 결정 (Gold-agnostic)**:
   - 분할기는 오직 원문 문자열 `text`만 입력받으며, gold 정답, BIO 태그, 문서 ID, 템플릿 정보를 일절 참조하지 않습니다.
   - 시그니처: `split(text: str) -> list[tuple[str, int, int]]` (끝 인덱스는 Python 표준 exclusive).
2. **원문 불변 및 무결성 보존**:
   - 텍스트 정규화(Unicode 정규화, 공백 압축, 철자 교정 등)나 정답 시작/끝 위치의 강제 조정을 일절 금지합니다.
   - 비공백 글자, 이모지(ZWJ 시퀀스 포함), 결합 문자(`\u0300` 등)가 1글자도 누락되거나 왜곡되지 않습니다.
   - 토큰 사이의 공백 외 텍스트 누락이 없음을 검증합니다: `text[start:end] == token`.
3. **학습과 추론의 동일 분할 규칙**:
   - 학습 데이터 생성 시 사용한 분할기와 B 파트의 추론 서빙 시 사용할 분할기가 동일해야 하며, 복원 규칙(`token_offsets`)도 완전히 일치해야 합니다.

## 4. B 파트 재사용 및 연동 인터페이스 제안

B 파트의 `GLiNERBackend`([gliner_backend.py](../../dev/detector/gliner_backend.py))를 수정할 때 사용할 수 있는 표준 어댑터 규격입니다:

### 4.1 의존성 및 패키지
- **외부 형태소 분석기(Mecab, KoNLPy 등) 의존 없음**: 순수 파이썬 표준 라이브러리(`re`)를 사용하며 추가 네이티브 패키지나 형태소 사전 설치가 필요하지 않습니다. 실제 Mac/Linux 환경의 Python·Unicode·분할 코드 버전을 기록하고 같은 사례로 검증해야 합니다.

### 4.2 공통 분할을 연결해야 하는 위치

기존 제안의 “backend `_tokens`만 교체” 예시는 제거했습니다. 그 방법은 창 계획만 바꾸고 GLiNER `predict_entities` 내부 분할은 기본값으로 남길 수 있습니다.

| 경로 | 같은 규칙을 적용할 위치 |
|---|---|
| 학습 | `tokenized_text`와 단어 span을 만드는 변환 planner |
| 모델 실제 예측 | `model.data_processor.words_splitter`를 사용하는 입력 분할과 위치 인덱스 생성 |
| backend 계획 | `_tokens`·`_plan`이 참조하는 같은 모델 분할기 |
| 문자 위치 복원 | 실제 예측에 사용된 토큰의 원문 코드포인트 offset |
| 저장본 재로딩 | 패키지 전처리 버전에 맞는 어댑터를 새 프로세스에서 다시 연결 |

공통 어댑터는 원문만 받아 `(token, start, end)`를 반환해야 합니다. 가중치 저장만으로 Python 분할 함수가 저장·재연결된다고 가정하지 않습니다. B와 합의한 로딩 인터페이스를 만들고 실제 모델 경로로 검증합니다. 후보 진단용 `SplitterPlanner`만의 성공은 이 조건의 완료 증거가 아닙니다.

### 4.3 위치 복원 (Offset Restoration)
- 분할기가 반환하는 각 토큰은 `(token, start_char, end_char)` 튜플입니다.
- 예측된 엔터티 `[first_word, last_word]`의 원문 위치는 다음과 같이 역산출됩니다:
  - `start = tokens[first_word][1]`
  - `end = tokens[last_word][2]`
- 위 관계는 학습·계획·실제 예측이 같은 토큰을 사용할 때의 복원 계약입니다. 조사·반복 문자열·이모지·URL·겹침 창 및 재로딩 사례에서 실제 예측 위치를 검증해야 합니다.

## 5. B 파트와 공동 합의해야 할 사항

1. **분할기 채택 승인**: `ko_atomic_suffix_v3` 또는 변형 규칙을 B의 실시간 추론 파이프라인에 도입할 것인지 여부.
2. **단어 수 증가에 따른 토큰 예산**: 분할 방식에 따라 단어·서브토큰·창 수가 달라집니다. 이전 제안의 15~25% 증가 주장은 실측 근거가 없어 확정 수치로 사용하지 않습니다. 실제 길이·창 수·지연을 측정합니다.
3. **B 운영 모델 패키지(`manifest.json`) 버전 갱신**:
   - `preprocessing.version`: `a-seg-candidate-ko_atomic_suffix_v3` 반영
   - A와 B가 동일한 패키지 스키마 및 전처리 버전을 공유하기 전까지는 배포를 진행하지 않습니다.

- 처리 기준을 확정하기 전에는 이 검사 결과를 `passed`나 학습 준비 완료로 바꾸지 않습니다.

## 3. 평가 자료에 어떤 한계가 있나요?

**개인정보 없는 정상 문장은 모든 분할에서 0건입니다.** 이 데이터만으로 정상 문장 오탐·오차단율을 평가할 수 없습니다. PRD의 별도 서비스 시험셋 300건에 정상 사례 100건 이상을 넣는 준비가 필요합니다.

**`PERSONAL_ATTRIBUTE`는 train에 2,460개 있지만 dev와 test에는 0개입니다.** 이 두 분할만으로 이 유형의 재현율을 확인하거나 임계값을 조정할 수 없습니다. 정답 개수가 0인 지표를 성능 0%나 100%로 해석하지 않고 평가 불가로 표시해야 합니다. 독립 서비스 시험셋에 해당 유형을 포함하는 방안을 검토합니다.

유형별 자료 수 차이도 큽니다. 첫 학습 표본을 단순히 앞에서 5,000건 잘라 사용하는 대신, PRD대로 분야·유형을 고려하는 이유입니다. 이번 단계에서는 학습 표본을 뽑지 않았습니다.

# 3단계 결과: 변환 도구 구현·검증 완료, 학습 자료 호환성 해결 필요

아래 §1~5는 **3단계 기본 분할 진단 당시**의 기록입니다. §6은 이후 후보 진단이며, 7.5단계 및 **8단계(시나리오 B)**에서 `ko_atomic_suffix_v3`와 경계 안전 창 처리(`_whole_group_plan`)가 B 프로덕션 런타임([`dev/detector/gliner_backend.py`](../../dev/detector/gliner_backend.py))에 최종 통합(`b_splitter_adoption=True`)되어 `verdict: "replace"`로 완결되었습니다([최종 보고서 v2](../report_v2.md)).

**3단계 당시 기본 설정으로는 PRD의 5,000건 학습으로 넘어갈 수 없었습니다.** 정확한 정답을 모두 보존한 train 문서는 2,635건이며, 같은 문장을 한 번만 세면 2,615건입니다. 상태는 `blocked_compatibility`입니다.

변환 코드, 거절 기록, 실제 토크나이저와 GLiNER 학습 배치 형식 검증은 준비했습니다. 아래 진단용 자료를 정식 학습 표본이나 공식 평가셋으로 사용하지 않습니다.

## 1. 2단계에서는 정상이었는데 왜 변환이 막히나요?

2단계는 원본 문장의 글자 위치와 정답 문자열이 일치하는지 확인했습니다. 3단계는 그 정답을 모델이 읽는 단어 위치로 정확히 표현할 수 있는지 확인합니다. 서로 다른 검사입니다.

예를 들어 `김가상에게`에서 정답은 이름 `김가상`입니다. 현재 B의 기본 GLiNER splitter는 전체를 한 단어로 읽습니다. 이 단어의 일부만 정답으로 가리키는 word-span이 없으므로, 원본 정답이 올바르더라도 그대로 변환할 수 없습니다.

조사까지 정답을 늘리거나, 이름 정답을 지우거나, 정답 위치를 보고 학습 자료에서만 단어를 쪼개지 않았습니다. 어느 정답이든 표현되지 않으면 문서 전체를 거절하고 사유를 기록했습니다.

## 2. 전체 30만 건 실제 변환 결과

| 분할 | 원본 문서 | 모든 정답 보존 가능 | 거절 | 가능한 문장 중 고유 문장 |
|---|---:|---:|---:|---:|
| `train` | 243,711 | 2,635 | 241,076 | 2,615 |
| `dev` | 28,147 | 577 | 27,570 | 570 |
| `test_track_a` | 28,142 | 120 | 28,022 | 119 |

실제 고정 토크나이저·라벨 prompt·B의 512 서브토큰/384단어/12단어 스팬 한도를 적용했습니다. 전체 실행은 로컬에서 약 27.2초였습니다. GPU 추론 속도나 탐지 성능 측정이 아닙니다.

| 분할 | 첫 거절 사유: 정답 경계 불일치 | 첫 거절 사유: 12단어 스팬 초과 |
|---|---:|---:|
| `train` | 239,561 | 1,515 |
| `dev` | 27,154 | 416 |
| `test_track_a` | 27,343 | 679 |

한 문서에 문제가 여러 개 있어도 위 표에서는 처음 확인한 사유 하나로 거절 문서를 셉니다. 상세 JSON에는 모든 정답을 개별 검사한 유형별 수치도 있습니다.

| 분할 | 경계·폭이 맞는 정답 | 단어 경계 불일치 정답 | 경계는 맞지만 12단어 초과 정답 |
|---|---:|---:|---:|
| `train` | 386,170 | 720,339 | 6,071 |
| `dev` | 37,982 | 85,121 | 416 |
| `test_track_a` | 36,361 | 84,017 | 798 |

문서에 있는 정답 한 개라도 보존할 수 없으면 문서 전체를 거절하므로, 개별 정답이 경계에 맞는 것과 그 문서를 학습 자료로 쓸 수 있는 것은 다릅니다.

변환 가능한 train 부분에는 다음 7개 유형의 정답이 남지 않았습니다: `KR_DRIVER_LICENSE`, `KR_PASSPORT`, `KR_NHIS`, `KR_VEHICLE_PLATE`, `USERNAME`, `PERSONAL_ATTRIBUTE`, `URL`.
따라서 작은 부분집합으로 임의 축소해서 학습하면 자료 수뿐 아니라 유형별 대표성도 PRD의 의도와 달라집니다. 5,000건 표본을 선정하거나 학습을 시작하지 않았습니다.

## 3. 무엇을 구현하고 검증했나요?

- 문자 끝 제외 위치를 단어 끝 포함 위치로 정확히 변환하고, 원문 위치로 역변환하는 검증을 구현했습니다.
- 한국어 조사·공백·반복 문자열·이모지·결합 문자·최대 스팬·부분 정답 창·라벨 순서·실패 기록 테스트를 작성했습니다.
- 전체 기본 테스트 104개가 통과했습니다. 데이터·네트워크·GPU 없이 실행하는 테스트입니다.
- 실제 GLiNER 0.2.29·Transformers 4.57.3·DeBERTa 토크나이저로 합성 경계 사례 6개를 검증했습니다.
- 실제 GLiNER collator가 고정 18개 라벨을 유지하고, 끝 포함 위치·같은 위치의 여러 라벨·정답 없는 예시를 CPU 텐서로 정확히 만드는 것을 확인했습니다.
- 모델 가중치, 가짜 모델 패키지, 가짜 예측 함수를 만들지 않았습니다. 토크나이저·배치 처리기와 B의 기존 계획 함수만 사용했습니다.
- 원본 3개 데이터 파일의 크기·SHA-256을 다시 확인한 뒤 진단 출력을 만들었습니다. 원본과 공식 분할은 바꾸지 않았습니다.
- 모든 원본 문서에 변환/거절 기록이 있고, 문서 수와 원본 정답 개수의 합계가 보존됨을 확인했습니다.
- 변환·실제 런타임 검사 프로세스는 네트워크 연결을 차단했고, 연결 시도 0회를 확인했습니다.
- Mac CPU 검증용 격리 환경의 패키지·확인값을 기록했고 `pip check`도 통과했습니다. GPU 서버의 설치 환경은 변경하지 않았습니다.

토크나이저 초기화에서 byte-fallback 및 upstream 정규식 경고가 관측되었습니다. 기존 B 설정을 유지했고, 탐지 품질 영향이 해결되었다고 판단하지 않습니다.

## 4. B와 맞춰야 할 결정과 다음 작업

권장 방향은 **정답을 보지 않고 원문만으로 결정되는 한국어 분할 방식을 A와 B가 함께 정하는 것**입니다. 형태소 기반 분할 같은 후보를 train/dev에서 검토할 수 있지만, 당시에는 특정 방식의 변환 가능량을 확인하기 전이었습니다. 이후 후보별 진단 수치는 §6에 기록했고 실제 공통 예측 연동은 7.5단계에서 검증합니다.

| 공동 확인 항목 | 필요한 이유 |
|---|---|
| 동일한 단어 분할·원문 위치 복원 | 학습과 실제 검사 서버가 같은 정답 경계를 사용해야 합니다. |
| 조사·숫자·기호·혼합 언어·긴 정답 처리 | 한 종류의 경계만 고치고 다른 유형을 망가뜨리지 않아야 합니다. |
| 12단어 스팬·384단어·512 서브토큰과 겹침 창 | 토큰 수가 늘어나도 원문과 정답을 잘라 버리지 않아야 합니다. |
| tokenizer·preprocessing·라벨 매핑 버전 | B가 같은 설정을 로딩하고 결과를 재현해야 합니다. |
| M0 기준선과 M1에 동일한 절차 적용 | 분할 설정 변경의 효과를 추가 학습 효과로 오해하지 않아야 합니다. |

분할 방식이 합의되면 전체 변환·역변환·커버리지를 다시 검증하고, 유형별 분포를 확인한 뒤 5,000건 표본을 선정합니다. M0 기준선도 같은 방식으로 측정합니다. 공식/독립 시험셋은 설정 선택에 사용하지 않습니다.

현재의 2,615건 부분집합으로 요구사항을 줄이거나 기존 B의 운영 splitter를 바꾸는 결정은 하지 않았습니다. 두 작업 모두 단순한 파일 형식 변환을 넘어 지원 범위와 평가 조건에 영향을 줍니다.

다른 분할의 중복은 문장과 문장 틀의 실제 내용을 내부적으로 비교해 찾습니다. 비교용 문장별 해시는 메모리에서만 사용하고 보고서에 내보내지 않습니다.

보고서에는 원문 문장·이름·전화번호·문서 ID를 넣지 않습니다. 문제 유형·분할·행 번호와 통계만 기록합니다. 공개 데이터 파일 전체의 SHA-256은 어느 원본을 검사했는지 식별하기 위해 기록합니다.

이미 있는 보고서는 덮어쓰지 않습니다. 변경 후 다시 검사할 때는 `data-audit-v2.json`처럼 새 이름을 지정합니다. 보고서에는 실행한 Python 버전, 검증 코드·자산 기준·원본 통계 파일의 SHA-256도 기록합니다.

현재 전체 검사의 기준 보고서는 [data-audit-v2.json](../reports/data-audit-v2.json)입니다. `v1`은 중복 발견 직후의 최초 결과이고, `v2`는 중복 문장 정답 일치 여부와 없는 라벨의 0건 표시를 추가한 결과입니다. 쉬운 해설은 [결과 요약](../reports/data-audit-summary.md)에 있습니다.

## 결과를 읽는 방법

| 상태 | 뜻 | 다음 행동 |
|---|---|---|
| `passed` | 구현한 구조·위치·분포·중복 검사를 통과 | 다음 단계의 학습 형식 변환 준비 |
| `needs_review` | 정답 겹침이나 같은 분할 내 문장 중복 등 검토할 항목 존재 | 원인을 확인하고 처리 기준을 기록 |
| `failed` | 잘못된 위치·파일 손상·분할 간 겹침 등 오류 존재 | 원본·검증 기준·수정 방법을 확인한 뒤 진행 |

같은 학습 분할에서 여러 문장이 같은 문장 틀을 사용하는 것은 정상입니다. 다른 분할에 같은 문장 틀이 나타나는 것은 학습과 시험이 겹치는 문제이므로 구분합니다. 겹치는 정답과 중복 문장은 조용히 삭제하지 않고 검토 대상으로 남깁니다.

문장 수와 분야별 개수는 다운로드한 전체 파일에서 다시 계산합니다. 오류 예시는 기본 20건까지만 저장하지만, 오류 건수는 전체 자료에서 계속 셉니다.

## 이번 검사로 알 수 없는 것

정답 위치와 문자열이 일치해도 그 정보의 유형을 의미상 올바르게 분류했는지까지 보장하지는 않습니다. 원본 BIO 정답과 문자 엔터티 사이의 완전한 의미적 정합성, GLiNER 토큰 변환·길이 처리, 모델의 실제 탐지 성능도 이 단계의 검증 대상과 구분합니다.

시험셋은 파일 구조와 정답 품질만 검사합니다. 모델 예측이나 점수를 계산하지 않으며, 시험셋 내용으로 학습 설정·임계값을 고르지 않습니다. 학습용 5,000건 표본 선정도 후속 단계입니다.

# 3단계: 정답 위치를 GLiNER 학습 형식으로 바꾸기

**이 문서는 3단계 기본 분할 진단의 실행 안내입니다.** 기본 분할에서는 고유 train 2,615건만 정답을 모두 표현할 수 있어 학습 준비가 차단됐습니다. 이후 한국어 후보(`ko_atomic_suffix_v3`)가 설계되어 7.5단계 오프라인 평가와 **8단계 B 프로덕션 런타임(`dev/detector/gliner_backend.py`)에 최종 통합(`b_splitter_adoption=True`, `verdict="replace"`)**되었습니다. [3단계 이력](../reports/conversion-summary.md), [공통 분할 제안](../segmentation/README.md), [최종 보고서 v2](../report_v2.md)를 함께 참고하세요.

아래 기본 변환 명령은 후보 분할을 실제 예측에 채택하는 명령이 아닙니다. 학습 예시의 분할·backend 창 계획·모델의 `data_processor.words_splitter`·문자 위치 복원을 함께 맞추고 재로딩 검증을 해야 합니다. 진단 부분집합을 정식 5k 또는 공식 시험셋으로 대체하지 않습니다.

## 무엇을 바꾸나요?

원본 정답은 글자 위치입니다. GLiNER 학습 정답은 단어 위치입니다.

```text
원문: 김가상 연락
원본 이름 위치: [0, 3) → 0번부터 3번 직전까지
단어 목록: ["김가상", "연락"]
GLiNER 이름 위치: [0, 0] → 처음과 마지막 단어 번호를 모두 포함
```

실제로 내보내는 한 예시의 형식은 다음과 같습니다.

```json
{
  "tokenized_text": ["김가상", "연락"],
  "ner": [[0, 0, "person"]],
  "ner_labels": ["person", "email address"]
}
```

위는 설명용 두 라벨 예시입니다. 실제 변환은 B의 임시 설명 매핑 18개를 고정 순서로 넣습니다. `ner_labels`는 원문 정답 문자열이 아니라 모델이 찾을 **개인정보 종류 목록**입니다. 원본의 `template_text`, `meta`, 기존 BIO 토큰은 모델 입력으로 넣지 않습니다.

## 정답을 맞출 수 없으면 어떻게 하나요?

`김가상에게`가 단어 하나로 나뉘면 모델의 단어 단위 정답은 전체 단어만 가리킬 수 있습니다. 이름 `김가상`만 가리키는 원본 정답과 맞지 않습니다.

- 정답을 조사까지 넓히지 않습니다.
- 정답을 보고 학습 자료에서만 단어를 쪼개지 않습니다. B의 실제 추론과 다른 기준이 되기 때문입니다.
- 이름 정답만 빼고 나머지를 정상 문장으로 학습시키지 않습니다.
- 그 문서 전체를 거절하고 사유를 기록합니다.

긴 문장을 나눈 창에도 같은 원칙을 적용합니다. 어느 창에 개인정보 일부만 남으면 그 창의 내용을 정답 없는 정상 자료로 내보내지 않습니다. 전체 원문과 정답이 보존된 문서만 진단용 출력으로 만듭니다.

## 기존 B 코드와 어떤 관계인가요?

새로운 운영 검사기를 만들지 않고 B의 `GLiNERBackend._tokens`, `_fits`, `_plan`을 재사용합니다. 실제 고정 GLiNER `0.2.29` processor와 DeBERTa 토크나이저를 사용합니다.

다음 제한을 함께 확인합니다.

- 한 창의 단어 수 최대 384개
- 정답 엔터티 하나의 최대 길이 12단어
- 라벨 설명·특수 토큰을 포함한 최대 512 서브토큰
- 서브토큰 계산 시 `truncation=False`로 단어가 사라지지 않는지 확인
- 창의 원문 위치와 재토큰화 결과가 일치하고, 모든 비공백 원문이 포함되는지 확인

기존 B 코드는 변경하지 않았습니다. 라벨 설명은 합의된 운영 설정이 아니라 [진단용 계획](../configs/conversion-plan.json)에 기록한 engineering 후보입니다.

## 실행 방법

현재 Mac에서 만든 전용 환경은 `model/.cache/conversion-venv`입니다. 로컬 CPU에서 토크나이저와 정답 텐서만 검사하며 신경망 가중치나 GPU 서버를 사용하지 않습니다.

다른 환경에서 재현하려면 Python 3.12 전용 가상환경을 만들고 [macOS arm64용 확인값 포함 패키지 목록](../configs/conversion-macos.lock.txt)을 사용합니다. **이 파일은 Linux/CUDA 서버 설치용이 아닙니다.** 서버 환경 계획과 별도로 보관합니다.

```bash
# 이미 준비한 전용 환경에서 작은 고정 토크나이저 파일 확인/준비
model/.cache/conversion-venv/bin/python -m model.data.prepare_tokenizer

# 기본 테스트: 실제 데이터·네트워크·GPU 없이 실행
model/.cache/conversion-venv/bin/python -m pytest model/tests -q

# 실제 토크나이저와 학습 배치 정답 텐서 검사
model/.cache/conversion-venv/bin/python -m model.data.verify_conversion_runtime \
  --tokenizer-dir model/.cache/tokenizer/a0484667b22365f84929a935b5e50a51f71f159d \
  --output model/reports/conversion-runtime-new.json

# 전체 문서 변환·거절 집계와 진단용 출력
model/.cache/conversion-venv/bin/python -m model.data.convert_dataset \
  --tokenizer-dir model/.cache/tokenizer/a0484667b22365f84929a935b5e50a51f71f159d \
  --output-dir model/.cache/conversion-new \
  --report model/reports/conversion-new.json
```

이미 있는 출력·보고서는 덮어쓰지 않습니다. 다시 실행하려면 새로운 이름을 지정합니다. 현재 기준 결과는 `conversion-v1.json`과 `conversion-runtime-v1.json`입니다.

`blocked_compatibility`와 종료 코드 1은 검사가 끝났으나 학습으로 넘어갈 조건을 충족하지 못했다는 뜻입니다. 입력·실행 오류의 종료 코드 2와 구분합니다.

## 출력 파일과 검사 범위

| 파일 | 내용 |
|---|---|
| `.cache/conversion-v1/<split>.diagnostic.jsonl` | 정답을 완전히 보존한 진단용 GLiNER 예시 |
| `.cache/conversion-v1/<split>.ledger.jsonl` | 원본 행별 변환·거절 상태, 창 위치·원문 역변환 정보 |
| `reports/conversion-v1.json` | 전체 문서·정답 개수, 유형별 불일치, 거절 사유, 실행 환경 |
| `reports/conversion-runtime-v1.json` | 실제 토크나이저·GLiNER 배치 처리기 검증 결과 |

진단용 예시는 정식 학습 표본이나 공식 시험셋을 대체하지 않습니다. 공식 분할과 원본 파일은 보존했고, 같은 분할 내 중복도 진단 출력에서 유지하며 고유 문장 수를 따로 셉니다.

공개 보고서에는 원문·개인정보 값·문서별 문장 해시를 넣지 않습니다. 실제 토큰이 들어 있는 예시는 Git 제외 캐시에만 둡니다. 전체 문서 수는 변환 수+거절 수와 일치해야 하고, 정답 개수도 같은 방식으로 누락 없이 집계합니다.

빠른 토크나이저의 byte-fallback 및 upstream 정규식 경고가 관측되었습니다. B의 기존 설정을 유지했으며, 임의의 자동 수정 플래그를 적용하지 않았습니다. 이번 검사는 위치·형식 검증이며 이러한 경고의 탐지 품질 영향은 별도 평가 대상입니다.
